## 1. Product Owner's explicit reprioritization

**Problem today:** the clinician opens a real appointment and sees the patient's display name, time and reason, but the Visit Brief says there is no confirmed clinical link and cannot show what happened last visit, what was planned, or what needs checking today. Clinic reports are used less frequently; visits are used throughout each working day.

**Clinician-visible v1:** keep Home unchanged. Tap Previous / Now / Next once. The same existing floating Visit Brief shows booking reason immediately; where a **verified exact booking → registered patient link** exists, additionally show concise (a) last signed/completed visit with date, (b) latest documented plan/decisions and relevant medication actions, (c) existing follow-up/awaited items and their *last recorded* status, (d) specific previously documented checks/purpose for today's visit; plus direct entrance to the already-protected selected-patient workspace. On first unlinked appointment, an explicit selection/confirmation creates only the bounded booking link; **automatic one-click reuse on later openings requires separately proven unchanged attendee continuity, not UID equality alone**. No candidate's private history is revealed before confirmation.

**Synthetic example:** “09:00 · follow-up, knee pain”. The first click shows time/reason and, after previously confirmed linkage, “Previous 22/09: assessment and explicit plan; Awaiting X recorded 22/09, status must be verified; Today: reassess Y from the previous NextContact”. If no signed evidence, show “Δεν υπάρχει προηγούμενη επιβεβαιωμένη καταγραφή”, not guessed treatment or tests.

**Not in v1:** Medical Reports #153 code/statuses, Clinical Inbox/Gmail, Reception messaging/voice/Cal booking writes, automated patient identification, invented clinical tasks/AI recommendations, GESY extraction, new patient registry, patient-data migration, changes to Visit Capture Save or the Home layout.

**Why this comes first:** repeated clinical use and existing verified protected sources. After one bounded independent affected R2 pre-code and separately authorized implementation, run finite synthetic tests, one affected exact-head post-code R2 and separate release decision.

Signed Visit Capture stores an authoritative reviewed candidate in `payload_json._visit_capture_v1` with `signed=true`, decisions, next contact, medications and source/provenance. - **Longitudinal context:** reuse supported G3 / signed history projections only when the clinical payload contract genuinely maps; do not copy a second independent longitudinal state engine into Cockpit.
- **Adjacent exact UID work:** RF × Secretary booking PR #159 is a separate **design-only RF-owned association** of issued RF and exact Cal booking. ## 3. Trust boundary: one verified booking link, persistent but narrow

### 3.1 Exact source identity and controlled confirmation

- A link addresses precisely **one** observed Reception booking namespace + immutable/opaque UID, normalized server-side without guessing prefixes or deriving from name/date/phone. Server revalidates the booking against the existing authenticated, bounded, **fresh Reception schedule** under the appropriate Cyprus-local target date; missing/incomplete/ambiguous/stale provider response fails closed. Booking details remain Reception-owned.
- The clinical patient ID comes only from an **explicit user-selected existing protected PatientORM**, after checking source/person identity using independently confirmed patient identifiers/evidence, not merely appointment display name. The interface can suggest search results but never preload their history or link them automatically. If Reception currently exposes only display name, it supplies **no strong auto-match evidence**; require clinician's explicit verification against independently available source and chart identifiers. An internal `patient_id` is not automatically an official GESY/identity number.
- A single confirmation action with visible patient + booking context and explicit `Επιβεβαίωση σύνδεσης` persists booking-specific association. Automatic subsequent protected opens **require the separately qualified same-attendee continuity contract below**; same UID alone does not suffice. Future appointments with different UIDs **remain unlinked** unless a future independently verified booking-person identity contract exists. Do not claim one manual link proves lifetime patient ↔ Reception identity.
- Store only necessary booking namespace/UID, selected protected patient ID, link state/revision, clinician confirmation/evidence **type** (not gratuitous raw national identifiers), booking identity hints/fingerprint for *detectible* conflicts (never as proof of same person), continuity qualification/version/token where supported, confirmation mode (`automatic_qualified` or `reconfirm_each_open`), event time and minimally attributable “confirmed via protected clinic operator” audit. Existing shared Clinical Key authenticates access but **does not establish an individual named clinician**, so never invent per-user actor identity.
- On changed/removed/cancelled booking, booking UID collision, substantive patient/identity-hint conflict, **missing or unprovable attendee continuity**, source coverage loss, link revision conflict or revoked link, **withhold patient-specific content** and offer re-confirmation. Simple rescheduling with stable trusted UID and consistent person can update displayed time from current source without silently changing clinical patient. Allow deliberate unlink/correction with optimistic version + audit; never overwrite another patient link silently. No linkage by fuzzy name, exact phone alone, date/time, recent-visit name or RF issuer.
- One narrow RF/Calendar-owned link record keyed by exact booking source+UID is acceptable **only after** comparing existing calendar import mapping and enforcing separation from mutable Reception source fields. Prefer a protected clinical/calendar sidecar in the existing configured database when the older `linked_patient_id` column cannot faithfully persist clinician-confirmed live booking links. No second patient master or external provider record writes. A table created with `create_all` cannot silently alter an existing live table. Define retention/correction/deletion and clinic access expectations within existing protected clinical policy before enabling identifiable live writes.

#### P1-01 correction — booking continuity is not person continuity (normative)

The existing `clinical_calendar.py` `ActualBooking` exposes `uid`, display name, clinic, start/end and reason/category, **not a stable person ID, attendee version, or authoritative identity-reassignment event**. A persistently equal UID can identify a booking while its participant changes. A changed person with the same displayed name or phone may be undetectable from this payload. Neither name, phone, clinic, dates nor any hash/fingerprint of those fields is sufficient to prove identity continuity, even if unchanged.

**Before enabling automatic same-UID patient brief reopening**, the existing Reception/Cal read owner must be independently qualified with producer-backed evidence of (A) an immutable unique UID→attendee binding including non-reuse, cancellation/replacement/reassignment semantics **or** (B) a provider-authoritative opaque stable attendee identity and/or revision assertion sufficient to detect replacement even when visible identity hints are unchanged. State the observed provider contract, namespace/normalization, qualification version and exact evidence in implementation/release material; a local assumption, code comment or matching UID/name is not qualification. A read-only extension of the *existing* Reception schedule projection may carry only the minimal opaque attendee continuity signal if available; **no new provider writer, second schedule engine, independent registry, raw identifiers, names/phone hashing as trust source or external effects**.

The protected server must revalidate fresh Cyprus-date source coverage, unique source+UID, current booking membership and **qualified same-attendee continuity on every brief read** before resolving the persisted patient link. Under that qualified invariant, a change of time with the same UID/attendee is a reschedule and may update displayed time; change/uncertainty of attendee, UID reuse/collision, cancellation, missing signal, contract change or stale/incomplete source **fails closed**. Confirmed UID-X cannot imply any patient match for different UID-Y.

**Mandatory safe fallback if qualification cannot be established:** persist the manually confirmed association for correction/audit but mark it `needs_reconfirmation` (not a resolved reusable authorization). On each later opening show **booking context only**; reverify the person's identity against independent protected chart/source evidence and require an explicit clinician confirmation **for that opening** before one bounded patient-specific read. No patient history/pending prefetch before reconfirmation, and no promotion of the link to auto-trusted simply because the same UID/name was observed again. This preserves safety while sacrificing one-click repeat access; **the requested one-click v1 outcome is not release-eligible until attendee-continuity qualification is demonstrated**, and implementation must report that limitation rather than assume it away. Confirmation, correction and revocation still use optimistic link revision, audit event and shared-key non-named operator attribution.

### 3.2 API/read contract, limited PHI

- Reuse the existing protected Calendar router and clinical data read owner. A bounded **read-intent** endpoint accepts only opaque booking UID in a protected request body, revalidates the current booking and link, returns **no clinical detail** for unlinked/invalidated/ambiguous booking. Only after the link is positively resolved **with qualified unchanged attendee continuity**, or after explicit independent person re-confirmation for the **current opening**, may an owned, minimal patient-brief projection read that patient's clinical rows. A persisted `needs_reconfirmation` record never authorizes a patient-specific prefetch.
- A bounded **explicit** clinician-confirm link/unlink endpoint owns versioned/auditable writes *only to the association*, never to PatientORM/EncounterORM/ClinicalPendingORM. No untrusted external content can choose a patient ID or an API action.
- Do not put patient identity, details, link tokens or clinical text in browser URL/history, logging, analytics, local/session storage or a public artifact. Clinical Key/cookie rules remain unchanged. Browser request generation must prevent late response for appointment A populating B, or old confirmed association surviving logout/auth loss.
- Brief payload contains source evidence/time and signed status; finite item caps and a clear `partial/unavailable` state. Do not send entire prior encounter payload, raw Dia text or a full unbounded patient history to the Home page merely to render four concise fields. No silent cache after closing or changing appointments.

## 4. First useful Visit Brief — source-verified read, not generated advice

**Context row:** currently selected booking date/time, clinic and literal/source-cleaned visit reason; note incomplete/stale schedule independently.

**Previous visit — P1-02 strict as-of booking rule:** “Previous” is **the latest supported, different, completed/amended patient encounter provably documented before the currently selected Reception booking starts**, not the last row at browser open time. Use the freshly source-verified **selected booking `start_at` instant** plus its `Asia/Nicosia` local date, never the browser clock, today's Home slot or encounter sorting alone. Filter `EncounterORM.patient_id` to the verified linked patient; require status `completed|amended` **and genuine clinical content**. A generic `visit_type` or status alone is not a clinical summary.

**Deterministic temporal eligibility:** (`encounter_date` ISO Cyprus-local date **strictly before** selected booking local date) OR (same local date **and** a credible signed/completed clinical instant **strictly earlier** than the booking start; for signed Visit Capture this is valid `_visit_capture_v1.signed_at`). Same-date date-only legacy records, invalid/missing instants, encounters at/after selected start and later-dated visits are excluded; do not turn the current visit into its own previous visit. Also reject content signed, created, updated or amended **at/after** the selected booking start when reconstructing what was known beforehand: if a later amendment overwrote earlier content and no verified earlier version exists, do **not** backdate it. Explicitly normalize UTC-naive ORM `created_at/updated_at`, aware signed timestamps and Cyprus DST when comparing. Sort only eligible encounters by date, trusted before-booking event instant and deterministic ID; finite caps. Prefer signed structured candidate with provenance, findings/change/impression only if actually present; unsigned/draft/unsupported content never masquerades as reviewed source. If temporal evidence is insufficient, show “Δεν επιβεβαιώνεται προηγούμενη καταγραφή πριν από αυτό το ραντεβού”, not a guessed prior visit.

**Previous decision / plan:** take validated `decisions`, medication actions and `next_contact` **only from the temporally eligible previous signed candidate** and its proven pre-booking version. Preserve clinical date, signed/source timestamps, source reference, verification and uncertainty; never substitute a later signed/amended/current encounter. A discussion is not administered treatment and a proposed dose is not an accepted plan.

**What is pending:** use the existing protected `ClinicalPendingORM` for the linked patient. Display item description, recorded status, origin encounter and review date if recorded; `resolved/cancelled/not_yet_indicated` must not be presented as currently open; only `open/awaiting_patient/awaiting_result` are unresolved-as-recorded. A pending row's current `updated_at/status` is **last recorded at read**, not reliable historic status as of a past booked appointment. For statuses currently lacking a reliable post-visit closure/update workflow, label as “Καταγεγραμμένη εκκρεμότητα — επιβεβαίωσε αν ισχύει” rather than asserting today's truth. Do not create CareTasks or resolve them by opening a brief.

**What to check for the selected booked date — P1-02 strict plan-date gate:** only the above temporally eligible signed previous candidate's explicitly stored `next_contact.purpose` / `next_contact.assess` may appear as planned checks **for this booking** if its valid `next_contact.when` **equals the selected booking's Cyprus-local date**. If `when` is missing, invalid, earlier or later, keep the recorded purpose/assess and original date (if any) under **“Προηγούμενο σχέδιο — χρόνος/συνάφεια μη επιβεβαιωμένα”**, not in “today” checks; never move the date, declare overdue or infer the next intended visit. Existing pending items may enter selected-date checks only as **“επιβεβαίωση της καταγεγραμμένης κατάστασης”** when their explicit `review_date` equals that booking date. Undated or nonmatching `review_date` remains historical/as-recorded pending, not assumed due. Use the label “Σήμερα” only if the selected Cyprus-local booking date actually is today's Cyprus-local date, otherwise “Για το ραντεβού [date]”. If no explicit source date-match, show “Δεν έχει τεκμηριωθεί συγκεκριμένος έλεγχος για αυτό το ραντεβού”. These are clinician-recorded intentions, never new diagnoses, derived deadlines, advice, generated checklists or actions.

**Fallback:** if no verified link, current schedule only plus obvious patient-confirmation action; if linked but no signed history, blank/unknown honestly. If clinical source 401/403, suppress protected content and offer common Clinical Key; if data source 503, retain no stale PHI and communicate which source unavailable.

**UI constraints:** enhance existing floating Visit Brief only; one click opens; linked patient immediately shows minimal history; one-tap “Κλινικός φάκελος” enters the current protected Cockpit patient workspace without changing Save authority. At split 680px / mobile 390px retain compact slots/Home and accessible overflow. Explicit back/close never mutates patient record or any provider, and no shadow “to-do” engine.

### 5.1 Bounded independent-R2 findings correction register

- **P1-01 — source-qualified attendee continuity:** Original design implicitly equated stable booking UID with the same person. Corrected: **UID equality is insufficient**; automatic protected same-UID reuse requires upstream-qualified immutable attendee binding or trustworthy opaque attendee revision. Since the current `ActualBooking` alone has no such evidence, the explicitly required fail-closed fallback is **booking-only + manual per-open re-confirmation**, not a fictional proof. Product one-click acceptance/release remains **conditional on future qualification** of the real producer/read contract.
- **P1-02 — previous encounter / selected-date semantics:** A previous visit must have supported content provably available before the **selected booking start**, including same-day signed timestamps and pre-booking amendment version; date-only or later-authored content cannot be backdated. A proposed check is “for this appointment” only on explicit `next_contact.when` or `ClinicalPendingORM.review_date` equality with selected local date; otherwise historical/as-recorded.
- **Exact evidence owners:** `clinical_calendar.py` `ActualBooking` / `CockpitAppointment` / live Reception reader, and `clinical_data.py` `EncounterORM`, signed `_visit_capture_v1.signed_at`, `VisitCaptureNextContact.when/assess`, `ClinicalPendingORM.review_date/status/updated_at`. No other design, UI layout, patient registry, Save or provider change.
- **Review state:** bounded author correction, **not an independent PASS**. Request exactly one independent **delta + affected cumulative pre-code R2** closure of P1-01/P1-02; inherit all unrelated PASS. No implementation, merge, deploy or real-PHI authorization.
