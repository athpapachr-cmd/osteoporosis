# Calendar appointment preview on the same page

## User correction and source evidence

After PR #297, clicking an appointment navigates to Cockpit and its booking preview. The clinician explicitly asks to remain on the calendar, see the appointment reason and restore the familiar floating appointment window. At `52b2832`, the calendar's prior dialog displayed the available appointment reason and a separate chart button; it did not itself automatically show the linked clinical summary. The current booking brief truncates the source reason to 240 characters; Reception can already truncate the source at 1,000 characters. Do not claim that the original source is complete.

## Proposed behavior and ownership

- Clicking a unique calendar row opens the calendar's existing accessible appointment dialog, keeping week, filters, search and scroll position. Display the available agenda reason clearly labeled while the protected read loads, or an explicit no-reason state; never infer a missing reason. Keep category/clinic changes optional via the existing separate options button; do not reintroduce generic first/review labels.
- For a unique booking, read the existing protected `/clinical/calendar/visit-brief/chart-read` with its booking UID and Cyprus appointment date, reusing that existing owner and its already-audited access behavior. Add `reason_available` (up to 1,000 characters from the same freshly resolved booking) and `reason_may_be_truncated` to this protected response's existing booking object only, without changing the original `reason` or other consumers' contracts. On success replace the displayed name, date, reason and booking action with these fresh response values before showing its associated clinical summary; do not compare only a 240-character prefix or mix agenda snapshot and fresh chart data. Explicitly indicate that the original may be longer when the available reason reaches 1,000 characters. Do not change booking, identity/link, clinical, provider or classification data. Its standard audit-access record still applies. Only an explicitly linked, server-validated chart may supply latest visit, previous decisions and open obligations; show truthful empty/unavailable states. Never link a patient by name or assume unlinked means a new patient.
- Retain a clear explicit action to open/link the chart through the existing booking-scoped Cockpit path. A user choosing that action may leave the calendar; ordinary preview/close does not. Do not implement a second patient association workflow.
- Duplicate booking UIDs, counted across the entire week before filtering, retain the existing safety warning and no chart-read/action. Verify response mode and canonical booking UID; use the freshly resolved booking response as one coherent source for displayed appointment details and its corresponding linked summary. A changed identity, time or reason replaces the old snapshot rather than being combined with it. The chart action is scoped to the fresh UID and date. Missing/invalid response data never exposes a clinical summary.
- Close, week reload, logout, expiry and a new selection invalidate/cancel pending reads and clear all patient/clinical content from the dialog. Delayed results cannot reopen or paint a different booking. Unauthorized/forbidden responses use existing protected-session clearing. Failure/timeout is visible but preserves the clicked booking reason when authentication remains valid.

## Review and evidence

R2: a new patient-linked read-only presentation surface reuses the existing identity, authorization and audit owner; pre-code design and exact-code independent review. Synthetic browser evidence must cover linked/unlinked results, full reason longer than 240 characters, no reason, source drift, duplicate identity across hidden/filter days, rapid switching/close/logout with delayed responses, auth failures, options and keyboard behavior, desktop/mobile layout, and one explicit path to existing chart. Use no real patient writes or patient-association changes.
