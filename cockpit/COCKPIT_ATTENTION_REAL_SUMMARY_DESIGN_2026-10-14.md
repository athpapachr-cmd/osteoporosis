## Product Owner plain-language checkpoint — CONFIRMED

Today the "Χρειάζονται προσοχή" card is mostly shortcuts, not the requested daily work summary. Product Owner explicitly approved a compact, source-backed one-tap attention summary: on a date with **exactly one pending scheduled surgery**, show patient name and procedure; where multiple surgeries share the same day, show the day count but **no names**. Show true RF issued/submitted/approved/rejected/scheduled/performed and own-actionable counts, with truthful unknown/unavailable states. Medical reports currently have no durable completed/pending ledger, so do **not** present fabricated counts; a separate bounded R2 report-status capability is needed. Email Inbox remains unconnected, not fake.

Concrete synthetic illustration: "Χειρουργεία · 3 εκκρεμή · 1 χωρίς ημερομηνία" followed by "Πέμ 15/10 · Ασθενής Δοκιμής Α · αρθροσκόπηση" *only* if there is one surgery that date. "Παρ 16/10 · 2 χειρουργεία" if two share that date. RF row: "Σύνολο 9 · Υποβλήθηκαν 3 · Εγκρίθηκαν 2 · Απορρίφθηκαν 1 · Πραγματοποιήθηκαν 1 · Δικά μου προς παρακολούθηση 2" (illustrative numbers, never production assumptions). Medical reports: "Δεν τηρείται ακόμη ιστορικό ολοκλήρωσης". Tap surgery → existing queue, RF → existing RF workflow, medical reports → existing report workflow.

## Scope for implementation after independent R2

1. **Surgery — reuse protected loaded queue.** `static/cockpit/app.js` already fetches `GET /clinical/surgeries`, containing `full_name, surgery_date, procedure_type` and published aggregate `cockpit:surgery-counts`. Extend that same in-memory event/payload, not a new endpoint or reader. Use dates already represented as local YYYY-MM-DD values (no timezone conversion of date-only values); compare with today's Asia/Nicosia ISO date when selecting upcoming days. Preserve existing `total` and `undated`, and derive dated group sizes with a bounded upcoming preview of up to three closest date groups; include a patient's `full_name` and `procedure_type` **only when exactly one pending surgical row has that same valid date**. For two or more, count-only, never names. Show overdue-date count separately and do not infer performed/completed from date; pending queue is authoritative. No names, clinical IDs, phone, DOB, surgery IDs in URLs, local/session storage, logs, browser badges or queue state shared outside the protected Cockpit. No new linkage; tapping opens existing queue without auto-selecting a protected patient. If source is 401/403, missing, stale/failed or not an array, show unavailable/login (never zero). Count and personal detail must clear on failure and only be shown while protected source is confirmed.

2. **RF — reuse existing read-intent search, no new backend or schema.** The already-protected RF `POST /clinical/clinic-utilities/rf/api/outcomes/search` accepts `{query:"",scope:"all",page:1}` and returns `counts`, `denominator`, `truncated`. Although POST, it is a read-only search and MUST NOT be confused with `/api/outcomes/{id}/events` or RF creation. Fetch on initial Home and `clinical:authenticated` refresh with same-origin credentials and no credential storage; use revision/race guard to ignore stale async responses and clear counts when unauthorized/unavailable. Validate integer nonnegative fields `denominator, counts.pending, approved, rejected, scheduled, performed, mine_actionable`. `denominator` is **issued attempts in the bounded source**, not 'still issued / awaiting submission' count; stage `issued` means outcome unknown, never mark as pending. The categories can overlap (e.g. approved later performed), so do not present them as an additive partition. `truncated=true` prohibits unqualified exact/all-time totals; show explicit partial coverage and no claim of exhaustive global totals (prefer withheld counts with a link to RF search). A blank/failed source is "Μη διαθέσιμα", not 0. Return no individual RF names or IDs to attention DOM. Link opens existing RF screen; my actionable amount refers only to explicit source-verified `mine_to_follow`, never auto-assign colleague applications.

3. **Medical report — truthfulness now, recording later.** `clinic_utilities/clinical_documents/report_api.py` currently exposes analyze/refine/research/preview/pdf with `autosave=False`, no case persistence; there is **no durable completed/pending report status ledger**. Home must say `Δεν υπάρχει ακόμη αξιόπιστη καταμέτρηση` and route to existing Medical Report, not print 0 or claim completion. A separately owned minimal protected report-status ledger (draft/complete/void and timestamp, issuer provenance, correction/retention/access rules, without raw PDF/transcript/signature storage) will require separate Product Owner acceptance and pre-code R2; **not included** in this Home-only implementation, and should not be quietly invented.

4. **Other unchanged authority.** Existing Inbox remains disconnected and badges truthful; Home search/recent 3, Visit Capture draft/Save/identity, appointment and Reception coverage remain unchanged; no new source/provider writes, no new credentials or analytics, and no extra action menu. UI remains concise at 390/680/1280px with one-tap access, no PHI in public CI artifacts: use fabricated names exclusively in test data/screenshots.
