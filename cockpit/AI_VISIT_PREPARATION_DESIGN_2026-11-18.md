# AI-assisted next-day visit preparation — design candidate

Base `5fda0eafab22774d412f4fd4baaf35ce22c320e1`. Product Owner requests one action preparing tomorrow's explicitly linked bookings, using the already integrated visit-processing AI. Output is a clinician aid, with factual chart content and AI questions visibly distinct; no automatic clinical decisions, edits, task creation or provider writes. A preference for how long to retain the results is pending and will be resolved before committing to storage behavior.

## Existing owners and scope

- Reception/clinical calendar owns the qualified booking and date; the existing clinician-confirmed booking link/audit owns patient identity. No patient identity is inferred by name, telephone or patient selection from the model. An unlinked, ambiguous, changed or missing booking receives a clear link-needed/unavailable status and no patient data is sent to AI. A clinician can use the existing booking preview to explicitly link it, then rerun that entry.
- Use the existing protected clinical session and `actor_for` authorization, fresh `_fresh_booking` target-day check, `_chart_reference` and `BookingPatientLinkORM` revision/namespace, access auditing, and `_minimal_brief` signed source projection. Latest signed/as-of visit, recorded plan/medications and bounded open obligations are displayed with their original status/time as source facts. No implicit claim of full chart, up-to-date medication reconciliation, results review or complete history.
- Extend the existing `AudioSettings`, project/key, retention gate, Responses transport and structured-considerations validator from `clinical_visit_audio`, without touching transcription or existing visit processing. Use a separate purpose-specific prompt that explicitly distinguishes the upcoming booking reason from prior signed notes and last-recorded pending status; clinician-facing possible questions are optional, not diagnoses, treatment orders or new tasks. Treat all chart and booking text as untrusted data, not instructions. Cap and structurally validate all provider output, accept only source IDs in the same patient request and optional purpose-linked/within-role considerations. If the booking reason or adequate source evidence is absent, show known facts with an honest reason rather than invent an AI question.
- Send only bounded clinical source excerpts and source-relative numeric IDs to the existing OpenAI project; never deliberately send patient ID, name, DOB, phone, booking UID, credentials or full chart JSON. Source free text may itself contain identifying information: do not claim de-identification. Responses `store:false` and the existing standard-retention mode apply; no logging of source/model output. Provider errors, timeouts or missing configuration show unavailable, not empty clinical record or completed preparation.
- Revalidate fresh booking observation, exact link state/revision and a keyed snapshot of the source clinical projection after the model response before displaying it; stale results are discarded, never attached to a different patient/booking. No DB session/transaction is held across the external call. Existing audit stores access metadata only. Authentication/authorization errors, logout, new load, explicit close, date rollover and affected link changes invalidate in-flight UI results.
- On demand from the existing tomorrow agenda, prepare linked bookings with one clinician action, bounded concurrency, clear per-booking progress and errors. The first version must enumerate all source rows and never silently skip beyond an undisclosed cap. Each ready patient opens the existing booking preview, displaying dated source facts and separate optional AI questions with source links/excerpts. Unlinked rows remain selectable through the existing explicit identity path and can be prepared after linking. No automatic background submission or patient communication. Refresh/retry is explicit when necessary; a previously unavailable source is not portrayed as empty.
- Retention is not yet frozen: in-memory session-only output is safe from clinical-record mutation but disappears when closed; persistent preparation across browser restarts requires a dedicated protected, expiring owner with explicit retention and deletion behavior, no patient-record overwrite and a separate pre-code data-owner decision. Do not use browser localStorage, logs, existing clinical task rows or implicit clinical Save to persist protected data. Do not start implementation on an undecided retention-dependent design.

## Gates and evidence

R2 for patient linkage, sensitive-data disclosure and AI clinical semantics. Independent pre-code review, bounded synthetic-only tests of authorization, exact appointment/date/patient identity, name collisions, unlinked/missing, source changes during provider call, no identifiers in deliberate model input, malformed/invented sources, no AI-write side effects, mixed batch failures, cancellation/logout/late completion, expiration/retention if approved, and actual browser desktop/mobile flow. Independent exact-code R2; final CI and separately evidenced release/smoke. No real patient/provider model calls during development or smoke.
