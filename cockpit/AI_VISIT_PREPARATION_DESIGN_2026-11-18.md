# AI-assisted next-day visit preparation — design candidate

Base `5fda0eafab22774d412f4fd4baaf35ce22c320e1`. Product Owner requests one action preparing tomorrow's explicitly linked bookings, using the already integrated visit-processing AI. Output is a clinician aid, with factual chart content and AI questions visibly distinct; no automatic clinical decisions, edits, task creation or provider writes. The Product Owner explicitly chose that preparations remain available the next day after closing the browser.

## Existing owners and scope

- Reception/clinical calendar owns the qualified booking and date; the existing clinician-confirmed booking link/audit owns patient identity. No patient identity is inferred by name, telephone or patient selection from the model. Normalize bare/prefixed UIDs identically to `chart-read` and use a booking copy with canonical UID before the HMAC/link check; test both formats. An unlinked, ambiguous, changed or missing booking receives a clear link-needed/unavailable status and no patient data is sent to AI. A clinician can use the existing booking preview to explicitly link it, then rerun that entry.
- Use the existing protected clinical session and `actor_for` authorization, fresh `_fresh_booking`, `_chart_reference` and `BookingPatientLinkORM` revision/namespace, access auditing, and the signed source selection behind `_minimal_brief`. Because `_minimal_brief` silently truncates some facts, the preparation must access validated full source items: transmit a complete bounded item or omit it with an explicit incomplete-source warning, never use a truncated excerpt as complete evidence. Apply the same limit truthfully to potentially upstream-truncated booking reasons. Test a negation/condition beyond the limit. Latest signed/as-of visit, recorded plan/medications and bounded open obligations are displayed with their original status/time and certainty/verification. `_minimal_brief` does not verify each pending item’s `source_encounter_id` belongs to the patient and is a valid signed eligible source: check that ownership and signed eligibility in a patient-scoped query before giving it to AI or offering a source link. If not proven, show only the recorded pending item as source-unverified, never read another patient or submit it as validated AI evidence. Test orphan and cross-patient source IDs. No implicit claim of full chart, up-to-date medication reconciliation, results review or complete history.
- Extend the existing `AudioSettings`, project/key, retention gate, Responses transport and structured-considerations validator from `clinical_visit_audio`, without touching transcription or existing visit processing. Use a separate purpose-specific prompt that explicitly distinguishes the upcoming booking reason from prior signed notes and last-recorded pending status; clinician-facing possible questions are optional, not diagnoses, treatment orders or new tasks. Treat all chart and booking text as untrusted data, not instructions. Cap and structurally validate all provider output, accept only source IDs in the same patient request and optional purpose-linked/within-role considerations. Additionally reject outputs that are not one complete bounded question. Existing `checked_considerations` verifies structure/IDs, not question form or medical correctness: even a valid question and cited IDs are unverified AI suggestions for clinician review, never established clinical truth. Test valid-structure imperative output, invalid citations and source-text prompt injection. If the booking reason or adequate source evidence is absent, show known facts with an honest reason rather than invent an AI question.
- Send only bounded clinical source excerpts and source-relative numeric IDs to the existing OpenAI project; never deliberately send patient ID, name, DOB, phone, booking UID, credentials or full chart JSON. Source free text may itself contain identifying information: do not claim de-identification. Responses `store:false` and the existing standard-retention mode apply; no logging of source/model output. Provider errors, timeouts or missing configuration show unavailable, not empty clinical record or completed preparation.
- `_minimal_brief` alone is as-of booking start, not as-of now. Qualify source selection against one frozen server UTC instant and Cyprus current day, excluding future-signed/future-dated entries even when they precede the tomorrow booking; retain this initial cutoff for provenance, but after AI independently rebuild a fresh as-of-T1 view or equivalent trustworthy watermark that catches new signed encounters, amendments and pending updates since T0; any source-set change invalidates the result. Preserve existing temporal behavior for all other consumers. Test future-signed, future-encounter and source changes during the provider call.
- `_fresh_booking` coverage does not guarantee that the selected booking is on the requested day. Explicitly require the returned booking start date in Asia/Nicosia to equal the requested day: tomorrow for first-batch generation and today or tomorrow for explicit regeneration, both before model dispatch and after the model response; midnight rollover or a move to another covered day fails closed with 409. Test before/during-call date moves, midnight and DST.
- Revalidate fresh booking observation, exact link state/revision and a keyed snapshot of the source clinical projection after the model response before displaying it; stale results are discarded, never attached to a different patient/booking. No DB session/transaction is held across the external call. Existing audit stores access metadata only. Authentication/authorization errors, logout, new load, explicit close, date rollover and affected link changes invalidate in-flight UI results. The batch queue is client-side only, with one protected request/result per distinct canonical booking UID and its validated linked patient_id, with bounded concurrency. Cancellation/close/logout stops admission of any new per-patient provider call, aborts active requests, and the server checks disconnection before and during provider work. Already transmitted content cannot be recalled; active provider cancellation is best effort. Test a multi-booking queue with concurrency one, abort during the first and prove no subsequent provider calls. Test two different tomorrow bookings for the same patient with different reasons, separate results and independent relinking; deduplicate only identical canonical booking UIDs.
- On demand from the existing tomorrow agenda, prepare linked bookings with one clinician action, bounded concurrency, clear per-booking progress and errors. The first version must enumerate all source rows and never silently skip beyond an undisclosed cap. Each ready patient opens the existing booking preview, displaying dated source facts and separate optional AI questions with source links/excerpts. Unlinked rows remain selectable through the existing explicit identity path and can be prepared after linking. No automatic background submission or patient communication. Refresh/retry is explicit when necessary; a previously unavailable source is not portrayed as empty.
- The Product Owner explicitly selected cross-browser-restart availability the next day. Use ONE dedicated expiring encrypted preparation table in the existing clinical database, not a clinical encounter/task or browser localStorage. Store only a unique keyed opaque digest of canonical `(namespace, booking UID)`, appointment date, expiry and generation metadata plus authenticated ciphertext of AI questions, source binding and freshness fingerprint; reconstruct the factual source projection from its existing owner when viewing, rather than duplicate source notes or demographics. Use AEAD AES-GCM from the declared `cryptography` dependency, a random unique 96-bit nonce per encryption, and versioned domain-separated keys derived from a dedicated server-only random 256-bit preparation secret, with independently qualified secure generation and fail-closed behavior when missing or invalid. Existing recovery-secret length alone does not establish entropy and is not used as proof of key quality. Canonical authenticated associated data binds namespace, keyed booking digest, target date, expiry and exact generation; reject swapped, tampered or mismatched rows. Do not add secrets or weaken existing gates. Test nonce uniqueness, row/ciphertext swap, tampering and key rotation. Lost/rotated secret means the draft is unavailable and must be regenerated. No plaintext AI or clinical content in SQL rows, logs or URLs.
- Default retention ends at the end of the appointment's Cyprus local calendar day. Expired data is never returned; encrypted active SQL rows are deleted opportunistically and by bounded periodic cleanup when the service is running. A sleeping service may delay logical deletion until it wakes. SQL deletion does not guarantee physical erasure from PostgreSQL dead tuples, WAL, replicas or backups; do not claim unverified backup retention or physical deletion. Clear explanation and explicit remove/regenerate controls. No startup DDL: reviewed one-table migration and minimal table-scoped SELECT/INSERT/UPDATE/DELETE grant to the existing app role, no schema CREATE grant. Database/access provisioning, merge and native deployment follow the previously authorized requested outcome, with source/permission qualification and no real patient writes during testing.
- After clinician initiation and protected booking/identity validation, a short-lived opaque reservation may be written before model dispatch; it contains no new clinical content. Publish the encrypted result only after identity, source and model checks pass. Expired empty reservations are cleaned up and are never returned as ready. Each canonical booking UID has at most one row, keyed by a domain-separated keyed digest; appointment date is metadata and authenticated binding, not part of the unique key. Rescheduling invalidates the previous-date draft/reservation and requires freshly verified booking and source; no duplicate row per UID. Each attempt reserves a unique non-reusable random generation token. Final publication is solely a conditional UPDATE against that exact still-existing, active, unexpired reservation; never a final insert/upsert. Delete, expiry, cleanup or cancellation invalidates the token, so delete→re-reserve cannot resurrect an older result (ABA). Keep independent `committed_generation` for authenticating the existing ciphertext and `pending_reservation_token` for the current attempt. Reserve changes only the latter; successful conditional UPDATE atomically installs ciphertext and its committed generation. A failure/cancellation clears only its own token and may leave earlier ciphertext accessible only after fresh source checks, without clearing a newer reservation. Test delete in flight, delete/re-reserve/old finish, cleanup during provider, two instances and failing newer generation. First batch generation is tomorrow-only. On every later open or explicit regeneration, permit the booking date to be today or tomorrow in Cyprus, and recheck that exact source date before and after AI and before returning protected data. On every later open, authenticate and verify live booking/date/link/revision and unexpired metadata, AEAD-decrypt only in server memory using the authenticated row metadata, verify the inner bindings and compare the stored keyed fingerprint to a fresh source projection, and only then return/render; on any failure return no plaintext or sensitive error details. a changed, expired, unverifiable or unreadable preparation is explicitly stale/unavailable and can be regenerated on the appointment day or the previous day. Midnight cancels in-flight/old UI but does not prevent a new authenticated read of a valid appointment-day draft; expiry is the next local midnight with DST-safe conversion. Never automatically overwrite the signed encounter or create obligations. User-triggered delete affects only this separate draft; audited metadata contains no free text. Privacy errors, logout, account change, client disconnect and day rollover fence in-flight results and close/cancel stops unstarted provider calls. Test process restart/browser restart, both days including DST, expiry, stale/relinked booking, key rotation, encrypted database inspection and concurrent generations.

## Persistence qualification details

- The stored keyed fingerprint is canonical and includes only material facts and source versions, booking reason and exact booking/link identity; it excludes display headings, read time and clock-relative labels. Unchanged facts remain valid across Cyprus midnight, while a changed signed record, pending item, binding or reason makes the draft stale.
- Expiry is evaluated using consistent database UTC time immediately before plaintext return and in the atomic commit predicate; an operation crossing local midnight cannot return or commit expired data. The expiry instant is the DST-safe conversion of local midnight after the appointment day.
- Key management must fence heterogeneous instances and rotation before any write: a keyed verification marker and version, stored in the same bounded table, are checked transactionally for every access/mutation. Provision a single securely generated key uniformly to all instances. Rotation requires all old instances stopped and reservations cancelled, then a reviewed atomic deletion of old drafts and marker before introducing the new key/version. No lazy rekey or mixed-key writes are allowed; marker mismatch fails closed, including in-flight publication. Lost/rotated keys make drafts unavailable. Test mixed instances, delete/recreate/old finish, rotation and same-booking regeneration. Never output secrets or sensitive exception content.
- The next-day discovery path begins with the current protected agenda after browser or process restart: a booking's preview queries its saved draft under the canonical UID and fresh link, without an AI call. Test separate same-patient and similar-name bookings, stale state, errors and relogin. Responses are `Cache-Control: private, no-store`; ciphertext and content never enter URLs or logs. Authentication failures/logout close and invalidate old views.
- Cancellation stops admission of new work. An observed cancellation before commit invalidates its reservation and prevents publication; network abort/disconnect is best effort and cannot guarantee the server receives it before a commit. An already committed encrypted result remains until explicit deletion or expiry and is subject to all fresh-read checks. Test both orderings.
