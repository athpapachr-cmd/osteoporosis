## Smallest final source design

```text
Cal actual bookings (booking UID/status/start/end/event type)
  → Reception-owned bounded, lightweight actual-schedule reader/cache
  → Reception schedule UI + private minimal schedule-context response
  → server-to-server Cockpit context reader
  → existing protected Cockpit Previous / Current / Next presentation

Cal ↔ Setmore + daily Clinical Calendar snapshot
  → off-hours/background reconciliation and Module-01 weekly Calendar only
```

1. **One operational source owner — FRESH-01 correction.** Reception reuses its existing Cal client/auth and schedule read, with a shared bounded query/projection for its UI and Cockpit. The lightweight reader makes **separate `status=past` and `status=upcoming` booking queries**: past covers appointments starting today in Asia/Nicosia plus a bounded previous-local-day lookback for a Current appointment spanning midnight; upcoming covers that same active boundary and the existing bounded future Next horizon. Both status streams must be paginated to an explicit complete end under the source's pagination contract and filtered against Nicosia-local bounds after retrieval; merge/deduplicate by booking UID and reject irreconcilable duplicate/status conflicts. A partial page ceiling, missing required status stream, provider failure or ambiguous completeness is unavailable, never a successful empty schedule. Include all actual eligible bookings regardless of ordinary/urgent event type; exclude cancelled/inactive bookings. An availability slot without a booking UID/status is never an appointment. Unknown event types remain ordinary `other` context; Aclasta gets the existing exception only from an explicit, reliable type mapping. A source-level test must show a booking returned only by `past` becoming Previous, a cross-midnight active booking becoming Current and a later `upcoming` booking becoming Next.
2. **Short-lived shared freshness — FRESH-02 correction.** Cache the complete actual-bookings projection for at most five minutes with single-flight concurrent refreshes. A cache miss or forced refresh has a **hard ten-second wall-clock deadline for both status streams and all pages combined**, with no automatic Cal retries on this read path and a combined ceiling of 20 pages at 100 bookings/page; reaching the ceiling without explicit completeness fails unavailable. Each provider attempt uses the remaining deadline, and cancellation/timeout does not publish a partial projection. These bounds are specific to the lightweight schedule path; the heavy sync's retry policy stays unchanged. Return the actual successful `fetched_at` and cache age; a cache hit must not reset freshness. Invalidate affected dates after Reception-owned create/cancel/reschedule success **and after an administrative `/sync/both` successfully changes Cal**; the heavy sync must not perform a foreground schedule read. A protected **Refresh schedule** action bypasses the cache, fetches actual bookings and redraws both schedule consumers' next request; it does not run `/sync/both`. On deadline/provider failure, show unavailable/stale age and retain no claim of live parity. No heavy sync or Setmore mutation occurs in the request path.
3. **Minimal cross-service read — FRESH-03 correction.** Reception exposes a private, bounded schedule-context response with booking UID, start/end, clinic, patient display name, source-proven human reason, event type/category needed for the existing overlap rule, and `fetched_at`; no phone, linked clinical patient ID, attendee payload, call context or raw Cal metadata. The current shared Cal client's `_request` prints full `resp.text` before projection. The lightweight bookings path must therefore use a scoped no-body-logging request mode (or a small safe extension of the existing Cal client): **never print raw booking response bodies, attendee data or booking payloads on success or failure**; log only non-identifying status, timing, page count and coded error metadata. Reuse the already deployed shared Clinical Calendar ingest secret strictly server-to-server for this read, with constant-time check and no browser exposure. Cockpit's existing protected same-origin `/clinical/calendar/cockpit-context` becomes a proxy/selector over that response, not a browser cross-origin call or a second Cal reader. It keeps the current concise response and fail-closed unavailable state.
4. **Separate weekly clinical projection.** The daily snapshot and normalized Clinical Calendar continue for the weekly Osteoporosis view and background reconciliation, without freshness authority for the global strip. Because global `other` rows are no longer needed in that store, the not-yet-released snapshot-only `retain_other` admission and its directly affected storage oracles are superseded before release. Preserve the accepted legacy-import discard/removal, manual overrides, weekly category filter and effective-`other` phone/link minimization. Do not delete any production rows by inference; D1.1 has not been deployed, and rollback/data treatment must be checked at release.
5. **Existing semantics survive.** Reuse/extract the implemented Nicosia day, start-order Previous, single active Current, strict earlier-Aclasta exception, overlap fail-closed and cross-day Next resolver. Keep the compact Home card, next-day date, weekly link, no counters/fallback, protected browser route, and no Visit Brief handler. No phone/name-based clinical identity linkage.
6. **Reception control correction.** Relabel the visible action `Ανανέωση προγράμματος` and bind it only to cache invalidation + lightweight Cal read + redraw. Keep `/sync/both` as protected administrative maintenance, not the visible routine action. Preserve the existing off-hours heavy cron and its call-agent safety boundary.

## Acceptance criteria for the revised D1.1 gate

1. With synthetic bookings, normal, Prolia/Aclasta and actual urgent booking `eventTypeId=393065` are eligible in one UID-deduplicated schedule; urgent/lab/telephone **availability** alone yields no appointment. A `past`-only completed booking can become Previous, an active cross-midnight booking can become Current, and an `upcoming` booking can become Next. Cancel/reschedule removes or updates the row after a successful fresh read; incomplete `past` **or** `upcoming` pagination, conflicts, page-ceiling and provider errors cannot masquerade as an empty complete schedule.
2. Reception and Cockpit read the same source projection. A healthy provider read is no older than five minutes under normal use; protected manual refresh forces a new read and redraw, including immediately after a booking change. A cached read reports its original fetch time. A synthetic slow/429/Retry-After source exceeds neither the ten-second total deadline nor the 20-page combined ceiling, does not retry automatically and yields unavailable without partial publication; heavy sync behavior remains unchanged. A successful administrative sync that changes Cal invalidates the affected cache without changing its off-hours cadence. `/sync/both` cannot be invoked by the visible refresh action, and the heavy cron remains off call hours.
3. Previous/Current/Next pass existing start-order, Nicosia DST/midnight, cross-day Next, explicit Aclasta and ambiguous-overlap tests. Unknown/urgent category does not silently become Aclasta. The weekly Osteoporosis Calendar stays filtered and linked.
4. Browser, cross-service response **and new schedule-read logs** never expose phone, linked clinical patient ID, raw Cal/attendee/call data or secrets; no name/phone clinical record linkage; auth failures fail closed. Server-side effective-`other` minimization and legacy import behavior remain intact. Synthetic PHI sent in a Cal booking response must be absent from success/error logs on the lightweight path.
5. Stale, failed or incomplete schedule reads show a plain-language unavailable/stale state with last successful fetch time when known; Cockpit never falls back to the daily Clinical Calendar as if current. A synthetic load/timeout check shows the lightweight refresh is bounded and does not invoke Cal↔Setmore or call-agent paths.
6. One affected-surface R2 pre-code delta review passes before runtime mutation. After implementation, one exact-head R2 fidelity review covers this revised source plus preserved semantics/privacy. Merge, deploy and production smoke remain separate decisions.
