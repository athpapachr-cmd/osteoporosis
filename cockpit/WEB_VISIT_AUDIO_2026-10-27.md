# Web visit audio in the patient chart — design candidate

> 2026-10-27, Asia/Nicosia. Product Owner explicitly superseded the prior local-only direction for this new web path. Real patient audio remains blocked until the OpenAI project is verified as Zero Data Retention (ZDR) and a purpose-specific Render gate is enabled. The prior local implementation remains available for rollback during the transition.

## One clinician path

The selected patient chart, reached from search or calendar, owns the encounter. Its existing visit composer gains an informed-patient control and direct Start/Stop microphone controls. Stop starts processing and returns a structured, editable clinical draft in the same composer. The clinician reviews the patient identity and draft, including uncertain statements and proposed obligations, and uses the existing protected Preview and one explicit Save. There is no background recording, automatic clinical write, raw-transcript display, or second patient-selection owner.

## Authority and provider boundary

- Reuse the existing Clinical Key protection, exact Visit Capture context, context-renew compare-and-swap, `VisitCaptureCandidateV1`, Preview and atomic context-consuming Save. The new endpoint has no database write and never creates a patient or encounter.
- A new `TranscriberProvider` consumes one bounded audio file and returns ephemeral text. `SummarizerProvider` consumes that text plus the selected chart's limited identity and date, and returns a strict `VisitCaptureCandidateV1`. OpenAI implementations use `gpt-transcribe` and Responses `gpt-6-luna` with Structured Outputs. Both IDs, timeouts, output limit and language/keyword hints are server configuration. No API key or provider configuration is sent to the browser.
- The server requires a purpose-specific `VISIT_AUDIO_OPENAI_PHI_APPROVED=1` in addition to `OPENAI_API_KEY`; existing document/Notion flags do not grant this purpose. This flag stays OFF until the OpenAI project ZDR state is verified. `store:false`, foreground Responses, no tools, and no file-storage endpoint are mandatory. The approved ZDR project/key mapping must be checked before setting the flag.
- The browser binds its recording to its selected `patientId`, composer generation and protected context. Before upload it renews the exact prior context if needed. The endpoint resolves the patient only from that context, checks it before and after both provider calls, and returns the same patient/context IDs. A stale, expired, changed or consumed context fails closed. The browser discards any response after a patient, session, context or draft-generation change.
- The provider sees audio/transcript and, solely for explicit identity-conflict detection, the selected name/DOB if present. The transcript is untrusted data. The model may not infer negatives, diagnoses, medication doses, completed actions, treatment choices or tasks from silence. It must separate options, recommendations, decisions, completed actions, preferences and uncertainty. Model output is parsed as one exact strict object, Pydantic validated, and checked for fixed source binding/date/provenance. Refusal, incomplete response, malformed content, identity uncertainty/conflict, or invalid provenance never reaches Save.
- The draft does not overwrite an existing visit. Pending obligations remain explicit editable candidates and enter the existing atomic Save only after final clinician action. Duplicate Save continues to consume a context once; uncertain network results require chart inspection, not a fresh write.

## Audio lifecycle and limits

- The recording starts only on a clinician click after an informed-patient checkbox and granted microphone permission. A visible indicator and elapsed timer remain until explicit Stop. Navigation, patient switch, logout, media error, page hide and the 30-minute ceiling stop tracks and discard incomplete audio.
- The browser uses WebM/Opus at a bounded rate; the first release accepts one file up to 24 MiB, under the documented 25 MB transcription limit. Oversize audio fails locally before upload. No arbitrary byte slicing or parallel chunking: a single file avoids cut words, reordering and multiple provider charges. Longer encounters can be revisited only under a separately reviewed chunk contract.
- The protected endpoint streams at most 24 MiB into a private mode-0600 temporary file, checks content type and duration claim, and removes the file in `finally` on success, failure, cancellation and timeout. It verifies the path is absent before returning. Audio and transcript are never stored in PostgreSQL, browser storage, logs or analytics. The browser releases its Blob after completion/error. Logical deletion is claimed only for the application's temporary path and in-memory lifecycle, not physical SSD erasure or provider internals.
- Normal logs contain route/status and sanitized error codes only. FastAPI/Pydantic/provider exceptions that could include content are caught before the HTTP/log boundary. No patient ID, audio, transcript, model request/response, or clinical draft is logged.

## Evidence and release gates

Pre-code independent R2 review covers external-data posture, identity/context authority, source semantics, deletion and the single-save boundary. Implementation tests use synthetic Greek-English medical text and synthetic audio bytes, mocked providers, stale/switching patients, malformed/refusal output, auth, duplicate Save and cleanup failures. Post-code independent R2 checks the exact code. Exact-head CI and Render configuration precede merge. Native `main` auto-deploy is observed once; production smoke uses static asset hashes, anonymous protected-route checks and PHI-free logs only. No actual patient audio or record write is part of agent verification. Real use waits for verified ZDR and clinician acceptance.
