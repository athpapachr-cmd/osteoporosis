# Web visit audio in the patient chart — design candidate

> 2026-10-27, Asia/Nicosia. Product Owner explicitly superseded the prior local-only direction for this new web path. Real patient audio remains blocked until the OpenAI project is verified as Zero Data Retention (ZDR) and a purpose-specific Render gate is enabled. The prior local implementation remains available for rollback during the transition.

## One clinician path

The selected patient chart, reached from search or calendar, owns the encounter. Its existing visit composer gains an informed-patient control and direct Start/Stop microphone controls. Stop starts processing and returns a structured, editable clinical draft in the same composer. After the result, the clinician explicitly confirms that the recorded encounter belongs to the displayed patient, reviews the draft and uses the existing protected Preview and one explicit Save. That confirmation resets on patient/context/session/draft changes. There is no background recording, automatic clinical write, raw-transcript display, or second patient-selection owner.

## Authority and provider boundary

- Reuse the existing Clinical Key protection, exact Visit Capture context, context-renew compare-and-swap, `VisitCaptureCandidateV1`, Preview and atomic context-consuming Save. The new endpoint has no database write and never creates a patient or encounter.
- A new `TranscriberProvider` consumes one bounded audio file and returns ephemeral text. `SummarizerProvider` receives numbered, immutable source units and returns **only source-unit IDs in bounded clinical categories plus an identity-state enum**, under a strict Structured Outputs schema. The server validates every ID and category, copies exact unit text deterministically into `VisitCaptureCandidateV1`, and validates the result again. It never accepts model-written clinical prose, values, source paths, dates, task status or medication structure. OpenAI implementations use `gpt-transcribe` and Responses `gpt-6-luna`. Both IDs, timeouts, output limit and language/keyword hints are server configuration. No API key or provider configuration is sent to the browser.
- The server requires a purpose-specific `VISIT_AUDIO_OPENAI_PHI_APPROVED=1` in addition to `OPENAI_API_KEY`; existing document/Notion flags do not grant this purpose. This flag stays OFF until the OpenAI project ZDR state is verified. `store:false`, foreground Responses, no tools, and no file-storage endpoint are mandatory. The approved ZDR project/key mapping must be checked before setting the flag.
- The browser binds its recording to its selected `patientId`, composer generation and protected context. It obtains a context before recording and renews that exact prior context just before upload. The endpoint resolves the patient only from that context and revalidates it **before transcription, between transcription and classification, and after classification**; it returns the same patient/context IDs. A stale, expired, changed or consumed context fails closed. The browser discards any response after a patient, session, context or draft-generation change.
- The provider sees audio/transcript and, solely for explicit identity-conflict detection, the selected name/DOB if present. The transcript is untrusted data. The strict schema has required arrays of integer IDs for `reason`, `history`, `finding`, `impression`, `option`, `recommendation`, `decision`, `completed`, `preference`, `follow_up`, `safety`, `administrative`, `uncertain` and `unclassified`, plus required `identity_state`. IDs must belong to the current bounded batch; duplicate or unknown IDs, extra keys, incompatible multi-category assignments, refusal or incomplete output fail closed. Every source unit must be accounted for; unassigned units become unclassified, never silently dropped. Units containing numbers, dose, laterality, negation or uncertainty are flagged for focused clinician review. No source unit may be promoted to a final decision/completed action merely because it describes an option, recommendation or future plan.
- The deterministic builder uses exact source text and fixed provenance `web_visit_audio`. It creates no medication fields, codes or durable pending obligations from model classification; explicit follow-up wording remains a reviewed fact until the clinician separately adds any task. It sets comparison `unavailable`, no inferred change, and the clinician-selected encounter date. If no reason or no meaningful clinical source can be safely classified, processing fails and the clinician may enter a manual draft. Identity `uncertain` or `conflict` fails before a draft is offered. Schema validation alone is insufficient: this exact-copy rule addresses the documented synthetic T-score mutation in free-form local summarization.
- A model ID in `recommendation`, `decision`, `completed` or `preference` is only a **provisional review hint**. Those exact source units enter the editable `uncertainties` section and a compact focused review list; the builder does not place them in typed recommendations/decisions/preferences or completed actions. The clinician may explicitly promote each item: select the required `DecisionType` for a recommendation/decision, select `PatientPreferenceStatus` for a preference, and confirm the statement describes an actually completed action before promotion. The UI removes the same unit from uncertainties only after that action. An unresolved item can stay visibly uncertain through Preview/Save; it is never silently omitted or given a default type/status. This is a separate clinician review action within the same draft, followed by the single final Save.
- The draft does not overwrite an existing visit. Preview accepts the draft without a patient-record write. For source role `web_visit_audio`, the protected Save contract additionally requires an explicit `recording_patient_confirmed=true` from the current review; absence/false is 409. Duplicate Save continues to consume a context once; uncertain network results require chart inspection, not a fresh write.

## Audio lifecycle and limits

- A protected read-only capability endpoint reports whether the distinct ZDR/purpose gate and key are configured. Start is disabled while unavailable; the upload endpoint independently enforces the same gate. The recording starts only on a clinician click after an informed-patient checkbox and granted microphone permission. A visible indicator and elapsed timer remain until explicit Stop. Navigation, patient switch, logout, media error, page hide and the 30-minute **browser** ceiling stop tracks and discard incomplete audio.
- The browser chooses supported WebM/Opus or MP4 audio at a bounded rate; the first release accepts one file up to 23 MiB, under the documented 25 MB transcription limit. Oversize audio fails locally before upload. The server enforces the byte ceiling; the browser timer is a UX limit, **not** a server-verified duration claim. No arbitrary byte slicing or parallel chunking: a single file avoids cut words, reordering and multiple provider charges. A server-enforced duration cap or longer encounters require a separately reviewed media probe/chunk contract.
- The protected endpoint streams at most 23 MiB into an anonymous mode-0600 `TemporaryFile`, which has no accessible pathname. The file is closed in `finally` on success, failure, cancellation and timeout; closed state is checked before any response. No detached task or background queue owns the file. A request-scoped disconnect watcher cancels provider work and closes its HTTP client. Each provider call and the whole pipeline have finite timeouts; timeout/cancel paths await cleanup before returning. Audio and transcript are never stored in PostgreSQL, browser storage, logs or analytics. The browser releases its Blob after completion/error. Logical closure/deletion is claimed only for the application's anonymous file and in-memory lifecycle, not physical SSD erasure or provider internals.
- Normal logs contain route/status and sanitized error codes only. FastAPI/Pydantic/provider exceptions that could include content are caught before the HTTP/log boundary. No patient ID, audio, transcript, model request/response, or clinical draft is logged.

## Evidence and release gates

Pre-code independent R2 review covers external-data posture, identity/context authority, source semantics, deletion and the single-save boundary. Implementation tests use synthetic Greek-English medical text and synthetic audio bytes, mocked providers, stale/switching patients, malformed/refusal output, auth, duplicate Save and cleanup failures. Post-code independent R2 checks the exact code. Exact-head CI and Render configuration precede merge. Native `main` auto-deploy is observed once; production smoke uses static asset hashes, anonymous protected-route checks and PHI-free logs only. No actual patient audio or record write is part of agent verification. Real use waits for verified ZDR and clinician acceptance.
