# Calendar independent labels — proposed R2 design for review

User behavior: on the compact calendar, choose visit type (unspecified, first visit, reassessment, other) and clinic (source/default, Limassol, Evrychou, other/unknown) independently per uniquely identified appointment. A filter for each axis operates on the displayed week. One appointment can simultaneously retain its current osteoporosis category, first/reassessment label and clinic label. User-assigned clinic is an organizational label in Cockpit; show the source clinic when different and do not claim to move the provider booking. The existing category editor and reset remain available.

Ownership and migration: extend existing `clinical_appointment_classifications` with nullable, allowlisted `visit_kind` and `clinic_override` columns; no second calendar, patient linkage, preference store, new database or schema CREATE permission. The existing non-null category must represent absence without changing automatic classification: store an empty string only when there is no manual category and decode it as null. A transactional, separately provisioned additive migration is required before new runtime starts; inspect actual table, application privileges and data first. No automatic DDL on startup or GET. Readiness must fail closed and deployment must not proceed if migration or role qualification is missing. Old runtime rollback must be blocked while new labels exist because its category reset deletes the row; roll back only to a compatible version that preserves new columns, or first export/preserve and explicitly migrate data.

Review correction: EVERY consumer of this row must decode an empty `category` as no manual override, particularly `_apply_import_item` and `calendar_rows`. The import/snapshot path must recompute the automatic category and must not delete an otherwise relevant appointment just because a label-bearing row has empty category. Synthetic tests must cover category reset with labels followed by import/snapshot and protected agenda. The existing `CalendarBase.metadata.create_all` must not be used to provision the extension; implementation must replace or guard the production startup path with read-only readiness, while preserving explicitly test-only schema setup and established tables. Verify all callers before choosing the smallest compatible change.

Code-review correction: a label write must re-read the complete Cyprus Monday-to-Monday week and require exactly one UID in that coverage-qualified fresh snapshot; a single-day check is insufficient. All three mutation axes (including existing category/reset) use a required expected revision and atomically reject stale edits; open old clients must reload before writing. Existing file-backed SQLite databases require the separately run, qualified additive SQLite migration; `create_all` cannot upgrade them. PostgreSQL readiness checks columns without DDL. Preserve the existing first-run local SQLite bootstrap only if neither calendar table exists; an existing or partial schema is never upgraded at startup.

Write safety: each update targets only one field, with SQL atomic insert-on-conflict/update, never read-modify-write of the whole record. Preserve concurrent writes to other axes. Category reset clears just category and must not delete rows bearing labels; row deletion only if all attributes empty and concurrency-safe. Enforce allowlists server-side, preserve current auth, no provider writes and no patient names in persistence or logs. Full JSON null is intentional reset to source/default. Return the stored field and authoritative revision; serialize same-field edits in UI, disable until result resolves, and on ambiguous timeout report uncertainty and reload committed state instead of retrying silently. If conflict control is needed, use server-side per-row revision compare-and-set, including all three existing/new mutation routes.

Identity: reject empty/noncanonical IDs and never match by name. Existing client-side duplicate UID guard across the unfiltered full week remains. For newly added label writes require a fresh authenticated source agenda spanning the supplied bounded week; ensure complete coverage, valid timestamps and exactly one canonical source ID over the complete returned source snapshot before allowing a mutation. Fail closed if source unavailable, stale, coverage incomplete, not found or duplicate. Source may change after the check: source IDs must be stable globally, and upstream ID uniqueness must be verified before implementation; if it cannot be proven, do not enable the write. Do not infer attendance or move a booking.

UI: fetch only via protected agenda, clear on 401/403/logout and invalidate stale responses; include labels in memory, filter without storing PHI/browser search. Present unknown vs explicitly chosen values, both effective clinic and provider source where they conflict. No auto-classification of first/reassessment from osteoporosis category or reason. Filter and counts respect all active filters, 5/7 visibility and empty cases; duplicate checks precede filtering.

Evidence: independently review feasibility against `clinical_calendar.py` producers and existing PUT/reset and schema/DDL owners before code; unresolved global identity or migration constraints block implementation. Tests with synthetic data cover simultaneous category/site/type, reset preserving other axes, concurrency and timeout uncertainty, server duplicate/source-freshness guard, source/default fallback, authorization and logout invalidation, 5/7/search/filters, SQLite and real PostgreSQL-compatible migration/rollback qualification. Independent exact-code R2 and CI follow. Actual DB migration and deployed operation remain separate from synthetic results.
