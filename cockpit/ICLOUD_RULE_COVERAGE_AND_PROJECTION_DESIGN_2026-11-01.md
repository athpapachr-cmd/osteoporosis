# Existing/new rules and no-rescan preference saves — design contract

Base fresh main85b8943d098f3912dddb5e14b41f8c718f68571d. Product Owner confirms the failed path is category+rule Save and explicitly chooses EXISTING AND NEW matching email, preserving individual classifications. Plain-category PR281 release is closed and insufficient for this path. This is a new R2 semantic correction, not a review of the closed review.

## Observed causes and boundaries

- Source confirmed: category Save with a rule supplies no single-item hint and falls into clear/page-reset/full-list loading. Rule-manager saves do the same.
- Read-only protected preference/header diagnosis: relevant rules are active but future-watermarked; subject terms and sender/domain independently restrict matches. No preference POST, message body/attachment, patient record or config access/mutation was used for diagnosis. Actual rule contents remain private; public examples are synthetic.
- Existing owner reuse: EXTEND the one existing operational preference document, canonical Python classifier, read-only mail router and volatile page view. Existing HMAC source-observation pattern in clinical_visit_brief.py establishes the primitive; new namespace is source-fact provenance only, never authentication or clinical identity. No new durable/cache store, dependency, role, connector or clinical writer.
- No merge/deploy/live-rule edits in this step. Prepare concrete existing-rule adjustment choices for separate release/clinician action; never silently widen saved sender/subject criteria.

## Rule coverage / legacy replay compatibility

1. Add strict optional bool `apply_existing=False` to RuleInput. Legacy absent value remains future-only. New UI defaults to existing+new for NEW rules, labels scope explicitly, and shows an explicit scope checkbox when editing existing rules. Existing stored criteria/scope are not automatically changed by deployment.
2. Canonical evaluation remains manual override > enabled matching rules > static suggestion. Same UIDVALIDITY always required. An active apply_existing rule ignores only its after_uid watermark; false/absent preserves current strict future-only comparison. Conflicting rule categories remain review. Mixed file-transfer services still require subject terms.
3. Existing rule edit retains the explicitly submitted coverage; disable/conditional undo preserve full previous rule snapshot. Scope cannot silently change on edit or mailbox epoch change; reactivation requires the existing explicit action. UI distinguishes inactive epoch, disabled, future-only and existing+new.
4. Adding a default field MUST NOT change hashes of any legacy operation. Before hashing, remove only nested rule.apply_existing when it is false, leaving the complete old canonical payload otherwise byte-identical. True is material and included. Existing category/rule/disable/undo receipt replay, stale retry, A/B/A and conditional undo keep their guarantees. No migrations/startup DDL/new table.
5. Explain sender/domain scope and that ALL supplied subject terms must occur in SUBJECT; empty subject terms match all subjects except mixed-transfer restrictions. Do not infer identity from sender/rule. Existing business-rule adjustments are deliberate separate preference edits after fresh CAS, never hidden rewrite in a reader.

## Canonical server reclassification of the retained source page

Do not introduce a second JS classifier or new server cache. Reuse canonical Python evaluation over bounded, server-proven facts of messages already viewed.

- In engine-bound list/detail responses, attach an optional private `projection_ref` to each qualified item. It is a versioned base64url JSON envelope with domain-separated HMAC-SHA256 using the existing Clinical Key, not a bearer credential. Payload binds server-derived mailbox scope, exact UIDVALIDITY/UID, source-capture timestamp, bounded existing display from/subject/date, parsed normalized sender, full normalized rule subject when representable by displayed content, and the original static suggestion before preferences. No body, attachments, recipient list, patient/visit linkage, credentials or hidden extra source content.
- Mint refs only from alias-qualified headers read through the existing IMAP adapter. If full rule facts would expose content beyond the bounded visible header, exceed the ref cap or cannot be faithfully represented, omit the ref; never truncate classification facts and then treat them as exact.
- New read-intent protected POST `/clinical/icloud-mail/category-projection` accepts1–25 unique UID-qualified items with optional refs. Bound total streamed body to256KiB, each ref to8192 ASCII bytes, decode/signature/schema/field lengths/number ranges strictly. Fixed safe errors; never log refs, headers, rule criteria or exception payloads. Existing Clinical Key/cookie auth and same-origin check required. Private/no-store response.
- Call the existing read-only source session only to qualify current configured scope/UIDVALIDITY. Verify HMAC in constant time and current scope/epoch/UID; auth/key rotation or configuration/epoch changes invalidate old refs. Refs are only historical captured-header facts, not current mailbox membership/read flags/provider truth. Every request still needs current auth. No ref is accepted as write/identity authority.
- For each VALID ref, classify the signed snapshot with ONE current preference DB snapshot and existing canonical precedence. Zero SEARCH, header/body FETCH or mailbox-wide scan. Preserve its original source-capture time; never refresh source freshness through reclassification. Missing ref may read only that exact UID's bounded headers through existing qualification and mint a ref if eligible; invalid supplied refs fail rather than silently downgrade. No body fetch, source flags or patient write. Worst case25 exact header reads, never unbounded/window SEARCH.
- Reply all requested IDs with category/origin and current server scope/epoch/revision. Classification is current for those captured facts; new/removed/source-changed mail requires explicit source Refresh. Do not claim refreshed source coverage, totals, membership, unread status or source timestamps. The endpoint performs zero preference/clinical writes.

## Frontend publication and UX

- Retain the existing page's source rows/cursors and selected body across every confirmed category/reset/undo/rule create/edit/disable. Abort/advance old generations and invalidate unread/source category caches immediately. Mark affected classifications as updating; disable stale controls. Do not empty the source page or navigate to page1 just because a preference was saved.
- Use the current auth-qualified server response as the committed revision floor, then request one bounded category projection for retained page IDs plus selected ID, deduplicated/max25. When no source page exists (e.g. rule manager alone), render committed rule state without starting a mailbox scan.
- Accept only complete validated projection IDs/scope/epoch, revision >= floor and current request/auth generation. No partial publication, no older callback refill. Projection may legitimately be newer than the triggering operation because every retained row is classified canonically from one current DB snapshot. Do not infer unchanged overrides from client history.
- Update only labels/filter visibility/editor state and rule manager from canonical results; retained message body/source fields and capture age stay unchanged. Rebind stale clinical/Pending search callbacks under current selection generation without opening/writing a patient. Rows moved out of current filter can disappear, undo can restore them; no automatic backfill/source scan. State explicitly that labels reflect the loaded section and source Refresh finds other/new messages.
- Rule manager opens without clearing retained source rows/page. Any live form drafts retain existing pending-Save locking and exact submitted-operation snapshots; broad reclassification must not erase other drafts or renew source age.
- Keep hidden unread preview revoked/unknown until explicit peek/Home policy refresh; no hidden scan following Save. Its unread/coverage truth always comes from existing read-only source adapter. Remote revisions/focus qualify current auth/preferences, and may reproject retained facts; never reuse old filtered categories.
- If projection/source qualification fails, retain only auth-qualified source headers/body with explicit unknown category state and retry/source Refresh choices; do NOT automatically reread the whole list.401/403 purge all protected DOM/data. Scope/epoch mismatch invalidates old source, requires explicit source reload and cannot resurrect old identities. No false Save after uncertain POST; replay/commit handling remains existing owner truth.

## Finite acceptance and review questions

Q1 Rule coverage: legacy future-only vs explicit existing+new, exact/domain/all-term matching, mixed-transfer safeguards, manual precedence/conflict, edit/disable/undo/epoch and old canonical operation hash compatibility.
Q2 Source provenance: refs minted only from qualified visible facts, no hidden PHI/body/recipient exposure, current auth/key/scope/epoch/UID bounds, strict size/shape/fixed errors, no new login/store/clinical authority, source capture age/membership limits truthful.
Q3 Projection: one canonical preference snapshot for all IDs; valid cached refs use0 SEARCH/FETCH; missing refs exact bounded headers only; readers write nothing. Newer/replayed/remote revisions cannot hide an unrefreshed manual change or accept stale projection.
Q4 UX: actual category+new-rule Save and rule-manager create/edit/disable/undo retain page/body/selection and use no full-list/peek scan; current filter/manual rows correct, source Refresh explicit, draft locks/concurrent callbacks/auth purge intact.
Q5 Regression: disposable PostgreSQL/SQLite + actual synthetic Chromium desktop/mobile with delayed responses, multiple writers, old hashes/replays, malformed/foreign/oversize refs, cold/absent refs, source epoch changes, disabled/missing stores and no clinical/provider writes. Reuse unchanged backend transaction evidence where applicable; no proposed-behavior execution before pre-code review.

One independent pre-code R2, then bounded implementation and targeted evidence, then one independent exact-code R2. Stop after finite gate closure. No production Save/rule adjustments, merge/deploy or broader owner/schema changes without later explicit authority. Rollback retains preference data, restores previous code/read-only labelled source behavior; no drop/grant/network changes.
