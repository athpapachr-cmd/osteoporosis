## 1. Product behavior, reuse and boundaries

- **One-tap detail action** on the selected RF attempt: **«Σύνδεση ραντεβού Γραμματείας»**. Clinician explicitly chooses a booking date to look up; UI displays fresh eligible Reception bookings for **that one date** as limited candidate cards with booking start/time in Cyprus, clinic, display name and brief reason when available (never phone). Candidates are *choices*, not inferred patient matches or verified identity.
- On deliberate selection and confirmation, protect **exact immutable RF application ID ↔ exact Cal.com source booking UID**. A clinician can unlink/relink with explicit confirmation; selection must survive neither lost auth nor a different selected RF. No saving client-side in localStorage, URL/query parameters or logs.
- On the selected RF detail, show **«Ραντεβού Γραμματείας επιβεβαιωμένο»** and the real local date/time **only while** independent evidence is fresh, unique, covered, active and RF scheduled date equals booking's Nicosia local date. Once valid, the weekly RF calendar may show the verified clock for that same issued RF date. The original RF progress status and manually entered `scheduled_date` are never automatically changed by a booking.
- If RF scheduled date is not yet recorded or booking date differs: keep link provenance and display **date-only** information with explicit pending/mismatch label, **no time**. User can separately record/correct the RF schedule through existing protected outcome action, then fresh recheck the link. No automatic “approved”, “scheduled”, “performed”, appointment creation/cancellation or notifications.
- No manual link => existing RF list/week retains **«Χωρίς επιβεβαιωμένη ώρα»**. A normal visit to 27 October does **not** automatically make an RF appear on that day's RF calendar unless the actual RF progress independently records the date.
- No second registry/patient-identity table, no copies of source booking snapshots, no change to shared Clinical Key, Clinical Calendar osteoporosis classification, Reception service/provider booking ownership, unrelated Cockpit Home counts, or patient clinical encounters. Reuse v1 Tracking [approved source design](RF_TRACKING_WEEKLY_CALENDAR_V1_DESIGN_2026-10-14.md) §5; this is the **separate R2 implementation-ready bounded data/link design**, not a replan of tracking.

## 2. Verified source seams and source contract

- Current `clinical_calendar.py` `ActualSchedule/ActualBooking` validates `uid,start_at,end_at,clinic,patient_display_name,reason,category,fetched_at,coverage_start,coverage_end`. It calls configured private Reception `RECEPTION_SCHEDULE_CONTEXT_URL` with `X-Clinical-Ingest-Key` from server environment; `/clinical/calendar/appointments` is **unsuitable** because it filters RF-like `other` categories. Reuse/refactor only the existing private source adapter in **this backend**, not a second browser/Cal.com reader or new secret.
- Read-verified Reception source: `athpapachr-cmd/ortho-reception-backend-v2` `schedule_projection.py` at verified main `bb591b519074317750940046b37fd7c30d0ef82f`, lines 86–141 and 169–179. Source paginates both past/upcoming, excludes `cancelled/canceled/rejected`, deduplicates exact UID, **fails closed on conflicting UID records**, exposes allowlisted booking fields without phone, and projects explicit coverage. This does **not** prove national-ID patient identity, nor source status beyond those provider filters.
- The source is eligible only if `fetched_at` is UTC-aware, absolute freshness `0 <= nowUTC - fetched_at <= 300 s`, coverage spans the **exact requested booking date** or entire requested week, provider snapshot is complete, all intervals UTC-aware and `end_at > start_at`, and the **exact UID is unique among returned active appointments**. If any precondition fails, no booking candidate for confirmation and no confirmed clock.
- Receiver never trusts user-supplied time, name, `category`, `status`, screenshot or arbitrary URL. Actual source only, server-to-server. Request failures/coverage unknown => `503 source_unavailable`, not confirmed cancellation. A confirmed missing UID under complete fresh coverage => `link_unverified` (hide clock); no destructive automatic unlink.

## 3. Single RF-owned association; schema and privacy

Add at most:
`clinic_rf_booking_links` — `application_id` (PK, exact issued attempt), `cal_booking_uid` (unique, not null), `revision` (int, optimistic), `linked_at`, `attestation_kind='clinic_key_clinician_explicit'`, `last_changed_at`. NO patient names, phone, reason, provider reservation snapshots, client secrets, real name of actor or PDF.
`clinic_rf_booking_link_audit` — append-only `id`, `application_id`, action `link|unlink|relink`, previous/new UID or bounded fingerprints (minimize if feasible), previous/new revision, UTC timestamp, attestation source `clinic_key`; no patient PHI, payloads or booking text. Explicitly document retention/deletion lifecycle for audit IDs before real clinical rollout, consistent with clinic policy.
- ORM in existing RF protected database. For deployed installations, migration plan must be explicit, safe, idempotent and verified on a synthetic existing-schema database. Creating new tables via current `RFBase.metadata.create_all` may be acceptable *only if* tested; no claim that `create_all` migrates existing columns/indexes.
- One-to-one unique indexes prevent same UID assigned to two different RFs. Handle concurrency by locking exact RF + association row, deterministic order and unique constraint integrity -> 409, never silently steal a UID.
- If user tries exact-ID RF deletion while a link exists, block with 409 and prompt explicit unlink before deletion. No orphan association or silent audit deletion. After unlink, ordinary exact-ID deletion still obeys existing linked-correction protection. Audit receipt must not leak clinical content.
- Existing RF issuance (A1/A2 immutable payload), RF progress/history, correction source, tracking cursor and Calendar stage changes remain unchanged. Shared Clinical Key is a clinic-wide authorization; audit labels **clinician attestation**, not verified per-doctor identity.

## 4. Protected API proposal (RF router; strict bodies; no raw UID in URL)

- `POST /api/outcomes/{application_id}/booking-candidates` with `{expected_progress_revision,booking_date}`. Requires current protected selected issued RF, fresh covered Reception read for **one** bounded date (Nicosia). Returns `{application_id,revision,source_as_of,expires_at,complete:true,candidates:[{booking_uid,local_date,local_start,local_end,clinic,display_name,reason_short}]}` sorted, bounded and no-store. No phone, no patient IDs, no unsupported categories; strict hard limit/503 if source incomplete or too many candidates.
- `POST /api/outcomes/{application_id}/booking-link` with `{expected_progress_revision,expected_link_revision,booking_uid,booking_date,clinician_confirmed:true}`. Re-fetch trusted source for exact date **before accepting**; recheck UID uniqueness/current RF revision/source coverage and date; transactionally create/change exact one-to-one link + audit. 401/403 Clinical Key, 404 RF/UID source-proven absence, 409 stale/conflicting UID/revision, 422 invalid missing confirmation, 503 untrusted/unavailable source. 200 response carries link revision and no presumed verified clock unless independently revalidated at display.
- `POST /api/outcomes/{application_id}/booking-unlink` with expected RF and link revisions, explicit confirmation; audit and commit atomically. No provider cancellation/changes; 404/409 stale failures.
- `POST /api/outcomes/{application_id}/booking-verify` body `{expected_progress_revision}`: exact selected link, fresh one-day source, checks RF `scheduled_date` and local booking date, returns minimal `{verified_time,local_date,local_start,local_end,clinic,source_as_of,expires_at,mismatch_reason,link_revision}` with `Cache-Control:no-store`. Never expose time when mismatch or unverifiable. Response not a durable source of appointment truth.
- Optional RF-week batch verification must read same week once, independently check **each existing linked RF**, and fail closed to RF **date-only** on any Reception/source failure; no N queries per card, no Home changes.

## 5. Volatile UI and absolute expiry

- Store selected RF ID/revisions and booking UID **in memory only**; separate `bookingGeneration` token from list, selected progress and week tokens; invalidate on RF switch, stale callbacks, navigation to builder, 401/403, loss of Clinical Key or protected response error. Don't overwrite a later valid source from an earlier response/error.
- Verified time expires **at or before source `fetched_at + 300 sec`**, even if page remains open and no network requests occur; schedule client hide and revalidate on focus, visibility change, selected RF/progress/link revision change, and each week/view display. Handle Nicosia DST with timezone-aware UTC interval conversion.
- Link-source 503/expiry/conflict/moved/canceled/uncovered/UID not unique: hide time/candidates, retain valid RF date-only timeline; stale source must never be shown as cancellation or as a fabricated zero. A date mismatch shows "Διαφορά ημερομηνίας RF/Γραμματείας — ώρα μη επιβεβαιωμένη".
- No automatic interaction with actual provider bookings, emails, medical reports, Reception call assistant or real patient data from this development task.
