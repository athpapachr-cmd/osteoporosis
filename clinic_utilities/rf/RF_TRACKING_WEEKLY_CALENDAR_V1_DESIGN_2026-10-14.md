## 1. Confirmed Product Owner experience

The embedded `Αιτήσεις & εκβάσεις` panel in the long RF form is hard to find. A clinician wants a **separate "Παρακολούθηση RF" page** with **Λίστα** and **Εβδομαδιαίο ημερολόγιο**, and visible direct navigation back to `Νέα αίτηση RF` / the existing A1/A2 form. A date in the RF ledger may be shown; an actual **Reception appointment with clock time** may be shown **only if there is an explicitly confirmed link to that exact RF application and a currently source-verified booking**. Do not infer it from patient name, surname, phone, type, approximate date, location or a free-text reason.

The desired UI is *iPhone-like*: compact, first-tap detail, no duplicated RF modules, no lengthy forms in the tracking list.

## 3. Tracking list contract

One authoritative RF application record = one issued attempt. An explicitly linked corrected RF is another attempt, not an alteration of the old rejection. Search by Greek patient name (accent/case insensitive), existing identity/GESY where authorized, issue date and optional stage; issuer filter only if source-backed. Show current lifecycle labels:

- `Εκδόθηκε — υποβολή άγνωστη` = `stage="issued"`; **not** "pending approval".
- `Υποβλήθηκε — αναμένει απόφαση` = `stage="submitted"` with explicit date, current pending.
- `Εγκρίθηκε` / `Απορρίφθηκε` = source-attested manual decision, including colleague-reported decision with **unknown submission date**.
- `Προγραμματίστηκε` / `Πραγματοποιήθηκε` only from the existing manually confirmed RF stage. Approval is not actual treatment.
- `Δικές μου προς παρακολούθηση` only if existing `mine_to_follow`, never because issuer was a colleague/default profile. Claims/releases do not change real outcome.

Card: name, RF anatomical site/side and A1/A2, issued date, latest recorded stage, issuer when documented and follow-up responsibility (source-backed). Select by **application ID only** within protected in-memory client state; stable optimistic revision on writes and stale-response isolation. No "quick action" can apply an event to another selected RF. Greek accent/case normalization, identity/GESY matching, issue date and status filters execute server-side across the reachable full RF ledger, never only page 1.

**P1-01 — complete server-side Tracking continuation, with legacy Home preserved:** Extend only the existing RF-owned `POST /api/outcomes/search` read handler with an **opt-in Tracking mode** (body-only `mode="tracking"`, filters and opaque `cursor`). The existing `query/scope/page` mode, `page ≤100`, response counters and `#152` Home `scope=all,page=1` consumer remain byte/meaning compatible, with no changes to Home denominator or count semantics. The dedicated screen uses `scope=all` by default and the new continuation mode; it does **not** paginate with the legacy page 100 ceiling.

In Tracking mode use a stable keyset over immutable issued attempts (`created_at DESC, id DESC`), a high-water bound for newly issued records and a protected, tamper-rejected continuation token bound to query, scope, all filters, sort, high-water and expiration. The token is transported only in a same-origin protected **POST body**, never document URLs, history, logs or persistent browser storage. Bounded server work per request scans forward from the **last scanned key** (not last matched record) and returns the next cursor even when a bounded scan yields zero matches. Repeated continuation must advance beyond both 2,000 visible results and 10,000 scanned records until a proved end-of-ledger; no artificial global page count, silent tail suppression or unbounded single-request scan. Source changes to mutable progress/stage during traversal trigger explicit freshness/restart or a clearly qualified partial state, never an asserted atomic historical snapshot.

Tracking responses strictly expose page items, `next_cursor`/`has_more`, `scan_complete`, `truncated`/incomplete reason and `source_as_of`; a resource ceiling or reader error is **partial/unavailable**, not proof of none. Show `Δεν βρέθηκαν αιτήσεις` only after a **complete filtered traversal**. Exact all-attempt counts/status totals may appear only if independently proven exact for the same filter/snapshot; otherwise mark as partial/unknown until verified, do not sum overlapping stage and approval outcomes and do not accumulate page-local counts as global. Selected writes invalidate affected searches and require fresh selected revision. Keep follow-up `mine_to_follow` strictly explicit/provenance-based, including colleague-originated RF, and issued without progress `υποβολή άγνωστη`. Do not create another RF list owner or registry.

The **existing RF action endpoint** remains the only authority for submission/decision/scheduling/performance. UI provides provenance/event date with explicit physician confirmation; auto-issued PDFs, calendar dates and actual Reception bookings **never** mutate `submitted/approved/scheduled/performed`. No GeSY provider submission or Cal.com booking write.

**Bounded read plan (P2-01):** after separate implementation authorization add one RF-owned protected read-only `POST /api/outcomes/calendar` with a strict Monday `week_start` (ISO local date). ## 5. Conditional Reception/Cal.com booking time — strictly verified link

### Current reality and optional RF-owned association

**No reliable link exists today.** Do **not** automatically match RF to a booking by name, phone, date, procedure keywords, patient ID guesses, issuer, or Cal category `other`. A list of anonymous matching suggestions cannot itself make a source link verified.

To enable future time display, define one **optional RF-owned, versioned one-to-one link** (`existing RF application ID ↔ exact source Cal.com booking UID`), under the **existing RF clinical database and protection**. If persistence is needed, at most one narrow RF-specific association sidecar (ID pair, association revision, recorded time, explicit clinician attestation, audit provenance); **NOT** a copied appointment register, new patient mapping table, secondary RF report owner, stored source snapshots or provider booking writer. A prior application ID and its immutable issued PDF remain unmodified. Require clear conflict behavior if UID is already attached to a different attempt; explicit unlink/relink with audit, no silent takeover. Existing RF outcome statuses are unchanged by linking.

**Two separate proofs are required before the UI says "Επιβεβαιωμένο ραντεβού Γραμματείας":**
1. A protected clinician explicitly selected **this RF attempt** and **that exact Cal UID** from source-backed booking choices, confirmed the association and the limited patient-context ambiguity. This is **manual association provenance**, not proof of individually authenticated clinician or national-ID identity. The shared Clinical Key remains clinic-wide.
2. At **display time**, the trusted server-only existing Reception schedule reader attests the **unique same Cal UID** in a fresh (age `0..300 seconds` by zone-aware UTC `fetched_at`), explicitly complete-covered source for the relevant booking date and requested week/day. The trusted Reception projection must be proven to exclude canceled/rejected bookings and reject conflicting UIDs; its current protected wire snapshot does **not** itself carry a per-booking `status` or RF ID, so do not invent one or rely on names/categories. The booked interval must have a valid UTC-aware start/end and Nicosia local date/time. **Additionally RF `scheduled_date` must exist and equal the verified booking's Cyprus date**; mismatch or no RF scheduling date blocks **clock time**, not date-only ledger rendering. Return only minimal linked facts to the protected RF detail (no phone, unrelated bookings or Home PHI), plus `source_as_of` and explicit clock expiry; never claim verified patient identity from name equality.

The **existing** `GET /clinical/calendar/appointments` is **not** sufficient for RF—it currently drops `other` bookings. Any necessary bounded sharing/refactoring of `clinical_calendar.py` must **reuse its existing protected Reception source/freshness/coverage reader**, not create a second direct browser/provider reader, a new credential, a Cal booking writer or broaden the osteoporosis screen. Future implementation may expose a narrow protected RF booking-candidate/link-verification read and an RF-owned audited link/unlink action, and must separately prove permissions and source coverage. If this integration cannot meet its source/auth/coverage gate, it **stays disabled**; deliver the full RF list/week with honest **Δεν υπάρχει επιβεβαιωμένη ώρα**.

**P1-03 — time is a continuously conditional display, not a permanent copied appointment:** Clock time is shown only while both link proof and every server-verification predicate above hold, with an absolute expiry of `verified_source_fetched_at + 300 seconds`. The protected client must proactively hide already rendered times **at or before expiry even without another fetch**, and recheck on focus, visibility regain, RF selection/link revision/schedule change and before every display; a refreshed server response must re-verify the current link/UID and data. Until fresh proof, show `Σύνδεση/ώρα μη επιβεβαιωμένη — έλεγξε Γραμματεία`.

On 401/403, 503, stale/uncovered/incomplete source, ambiguous/changed/missing UID, conflict, source-confirmed cancellation, malformed interval, changed RF date or **different booking date**, immediately remove the previously displayed time; a failing/uncovered source does **not** prove cancellation. If the same UID was moved to another date, optionally retain **date only + discrepancy warning**, require manual audited RF schedule correction and subsequent complete source re-verification before enabling the **time**; never automatically modify `scheduled/performed` or create/reschedule/cancel/notify Cal.com. If no verified RF↔booking association or trusted verification is feasible, booking-time capability stays **OFF** while list/week remain functional.

### Read race/authorization

**P1-04 — separate asynchronous streams + global authorization epoch:** Keep independent monotonically increasing request generations for **(a)** search/list and filters/cursor, **(b)** selected RF/detail/outcome writes, **(c)** week/source date-only calendar and **(d)** optional booking candidates/link verification/times. Each response or error applies only if its own latest generation, active RF ID + revision (where applicable), search scope/filter, selected week and current shared authorization epoch still match. A newer week request must not invalidate a valid list response, and a stale booking response must never overwrite a newer selection. A stale failure A after success B is ignored, as is stale success A after B error.

On shared Clinical Key logout, re-auth, session expiry or any 401/403, synchronously increment **global auth epoch**, invalidate all stream generations, clear previously protected RF names/details, booking candidate/UID/time and any pending correction intent, until fresh authorized reads. On an RF ledger 503/network/malformed response invalidate and hide **the affected protected RF view**, show unavailable/partial not a false zero; prevent old success from restoring it. On a Reception-only 503/staleness/coverage/malformed response invalidate and hide **only booking candidates/linked clock times**, not a valid RF date-only week/list; do not fabricate "no RF". A link/date mismatch or failed verification clears time only. Never cache identifiers in URL, browser storage, screenshots or telemetry; server-returned sensitive fields stay within authenticated RF screens. Require strict `complete/truncated` validation and independent error/loading/empty states in synthetic Chromium.
